遊戲 Plane 使用範例

示範遊戲類專案的 Plane.io 結構與實際填寫方式,對應核心規範「Plane 開立規則」的通用欄位/卡片規則。遊戲的拓撲是單一共用專案「遊戲開發商」,所有老虎機/棋牌/迷你遊戲的開發工作都在同一個專案裡,用模組＝哪一款遊戲、標籤＝哪個部門區分,不是各部門各自獨立成專案。

模組與標籤總覽

維度用途例子
Module（模組）對應單一一款遊戲，從規格到上線都是同一個模組，模組進度％＝這款遊戲的整體完成度01.荷魯斯之眼、02.金虎爺、03.巨亨麻將、04.門神、05.釣蝦王...
Label（標籤）對應部門／專業別，同一張工作單同時掛模組（哪一款）與標籤（哪個部門）企劃與數值、美術與動效、伺服器/後端、音效與音樂、客戶端/前端、QA測試驗證
部門（Label）每款遊戲的顆粒度完成狀態追蹤方式
企劃與數值通常 1-2 項(規格書、機率外包交付),不逐項拆單一完成狀態
美術與動效（原畫部分）逐項素材工作事項(如百餘項/款)單一完成勾選,前端自行從整批原畫抓進度,不逐項對應驗收
美術與動效（動效部分）逐項動效工作事項雙重驗收:動效組完成 + 前端套用完成,兩者各自開一張工作事項,用 Plane 關聯(relation)連結
音效與音樂逐項音效工作事項單一完成狀態,完成後整批交付前端套用,不逐項對應驗收
伺服器/後端依規格拆分的工作事項,依賴機率外包交付單一完成狀態
客戶端/前端對應動效逐項開「前端套用」工作事項(relation 連回動效);原畫/音效/後端則是較粗顆粒度的整合工作事項依項目類型而定
QA測試驗證測試驗證工作事項,含機率/RTP模擬驗證單一完成狀態

「上線」歸在企劃與數值部門的最後一項,不獨立成部門。

Cycle（週期）排法範例

週期對應各部門固定的作業階段，不對應「一整款遊戲」；一次只建立「目前＋下一個」週期，比照核心規範「Plane 開立規則」的 Cycle 使用原則。以美術與動效（原畫）為例：

週期時長內容
原畫_收集方向2 週蒐集參考、確定美術方向與風格
原畫_實作出圖4 週正式繪製與出圖，完成後接續下一款遊戲的「收集方向」週期

動效、客戶端/前端、伺服器/後端等部門比照同樣概念（收集／規劃階段＋實作階段兩段式週期），實際時長依部門與工作量調整，非固定 2+4 週。

PM+企劃 年度規劃 → 與需求方確認 → 年度計畫拍板
        ↓（單一遊戲流程開始）
企劃產出規格書
        ↓
        ├─→ 機率（外包）完成 ──────────────┐
        └─→ 美術原畫完成 → 分成兩份：      │
                 ├─→ 前端（套用靜態美術）   │
                 └─→ 美術動效完成 → 同時交給： │
                          ├─→ 音樂音效（依動效做設計） │
                          └─→ 前端（逐項套用動效，relation 對應） │
                                   ↓                  │
        後端（依賴機率邏輯） ←──────────────────────────┘
        後端完成、音樂音效完成（整批交付） → 前端最終整合
        ↓
前端自測 → QA 完整測試驗證（含機率/RTP模擬驗證） → 驗收沒問題 → 安排上線

清單(xlsx)與 Plane 的關係

原畫/動效/音效目前是人工雙軌:各單位在 xlsx 清單(如 巨亨麻將_原畫清單.xlsx、荷魯斯之眼 動畫清單.xlsx)勾選完成度做內部工作追蹤,同時也要手動同步更新 Plane 上對應工作事項的狀態。xlsx 清單是 Plane 卡片連結的「連結文件」,不是取代 Plane。

實際填寫範例

遊戲最容易搞混的地方是三種素材單位的驗收方式完全不同:原畫單一驗收、動效雙重驗收(relation)、音效整批交付。以下用真實素材命名示範三種情境。

範例1:原畫(單一驗收,無 relation)

標題[原畫][巨亨麻將] logo_game 遊戲LOGO
Module巨亨麻將
Label美術與動效
Assignee原畫 王美術
Reviewer原畫組長
StatusDone
內容檔案位置 ui/branding,時數16h

清單全數完成後,前端自行從整批原畫抓進度開始套用,不會針對這張卡另開一張對應的前端工作事項。

音效清單全數完成後,整批交付前端套用,不會逐項開對應的前端工作事項。
