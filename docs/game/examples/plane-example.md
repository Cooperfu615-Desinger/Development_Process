# 遊戲 Plane 使用範例

本文件示範遊戲類專案的 Plane.io 結構與實際填寫方式，對應核心規範（`docs/core/SOP.md`）「Plane 開立規則」的通用欄位/卡片規則。遊戲的拓撲是**單一共用專案「遊戲開發商」**，所有老虎機/棋牌/迷你遊戲的開發工作都在同一個專案裡，用**模組＝哪一款遊戲、標籤＝哪個部門**區分，不是各部門各自獨立成專案。

## 模組與標籤總覽

| 維度 | 用途 | 例子 |
|---|---|---|
| Module（模組） | 對應單一一款遊戲，從規格到上線都是同一個模組，模組進度％＝這款遊戲的整體完成度 | 01.荷魯斯之眼、02.金虎爺、03.巨亨麻將、04.門神、05.釣蝦王... |
| Label（標籤） | 對應部門／專業別，同一張工作單同時掛模組（哪一款）與標籤（哪個部門） | 企劃與數值、美術與動效、伺服器/後端、音效與音樂、客戶端/前端、QA測試驗證 |

| 部門（Label） | 每款遊戲的顆粒度 | 完成狀態追蹤方式 |
|---|---|---|
| 企劃與數值 | 通常 1-2 項（規格書、機率外包交付），不逐項拆 | 單一完成狀態 |
| 美術與動效（原畫部分） | 逐項素材工作事項（如百餘項/款） | 單一完成勾選，前端自行從整批原畫抓進度，不逐項對應驗收 |
| 美術與動效（動效部分） | 逐項動效工作事項 | 雙重驗收：動效組完成 + 前端套用完成，兩者各自開一張工作事項，用 Plane 關聯（relation）連結 |
| 音效與音樂 | 逐項音效工作事項 | 單一完成狀態，完成後整批交付前端套用，不逐項對應驗收 |
| 伺服器/後端 | 依規格拆分的工作事項，依賴機率外包交付 | 單一完成狀態 |
| 客戶端/前端 | 對應動效逐項開「前端套用」工作事項（relation 連回動效）；原畫/音效/後端則是較粗顆粒度的整合工作事項 | 依項目類型而定 |
| QA測試驗證 | 測試驗證工作事項，含機率/RTP模擬驗證 | 單一完成狀態 |

「上線」歸在企劃與數值部門的最後一項，不獨立成部門。

## Cycle（週期）排法範例

週期對應各部門固定的作業階段，不對應「一整款遊戲」；一次只建立「目前＋下一個」週期，比照核心規範「Plane 開立規則」的 Cycle 使用原則。以美術與動效（原畫）為例：

| 週期 | 時長 | 內容 |
|---|---|---|
| 原畫_收集方向 | 2 週 | 蒐集參考、確定美術方向與風格 |
| 原畫_實作出圖 | 4 週 | 正式繪製與出圖，完成後接續下一款遊戲的「收集方向」週期 |

動效、客戶端/前端、伺服器/後端等部門比照同樣概念（收集／規劃階段＋實作階段兩段式週期），實際時長依部門與工作量調整，非固定 2+4 週。

## 依賴關係

```
PM+企劃 年度規劃 → 與需求方確認 → 年度計畫拍板
        ↓（單一遊戲流程開始）
企劃產出規格書
        ↓
        ├─→ 機率（外包）完成 ──────────────┐
        └─→ 美術原畫完成 → 分成兩份：      │
                 ├─→ 前端（套用靜態美術）   │
                 └─→ 美術動效完成 → 同時交給： │
                          ├─→ 音樂音效（依動效做設計） │
                          └─→ 前端（逐項套用動效，relation 對應） │
                                   ↓                  │
        後端（依賴機率邏輯） ←──────────────────────────┘
        後端完成、音樂音效完成（整批交付） → 前端最終整合
        ↓
前端自測 → QA 完整測試驗證（含機率/RTP模擬驗證） → 驗收沒問題 → 安排上線
```

## 清單（xlsx）與 Plane 的關係

原畫/動效/音效目前是人工雙軌：各單位在 xlsx 清單（如 `巨亨麻將_原畫清單.xlsx`、`荷魯斯之眼 動畫清單.xlsx`）勾選完成度做內部工作追蹤，同時也要手動同步更新 Plane 上對應工作事項的狀態。xlsx 清單是 Plane 卡片連結的「連結文件」，不是取代 Plane。

## 實際填寫範例

遊戲最容易搞混的地方是三種素材單位的驗收方式完全不同：原畫單一驗收、動效雙重驗收（relation）、音效整批交付。以下用真實素材命名示範三種情境。

### 範例1：原畫（單一驗收，無 relation）

| 欄位 | 內容 |
|---|---|
| 標題 | [原畫][巨亨麻將] logo_game 遊戲LOGO |
| Module | 巨亨麻將 |
| Label | 美術與動效 |
| Assignee | 原畫 王美術 |
| Reviewer | 原畫組長 |
| Status | Done |
| 內容 | 檔案位置 `ui/branding`，時數16h |

清單全數完成後，前端自行從整批原畫抓進度開始套用，**不會**針對這張卡另開一張對應的前端工作事項。

### 範例2：動效 + 前端套用（雙重驗收，relation）

**動效卡：**

| 欄位 | 內容 |
|---|---|
| 標題 | [動效][荷魯斯之眼] clip_1 MG背景動畫 |
| Module | 荷魯斯之眼 |
| Label | 美術與動效 |
| Assignee | 動效 張動效 |
| Reviewer | 動效組長 |
| Status | Done |
| 內容 | 播放時機：循環播放；動畫長度270f |
| 相依關係 | blocks → 下面的前端套用卡 |

**前端套用卡（與動效卡用 relation 連結）：**

| 欄位 | 內容 |
|---|---|
| 標題 | [前端][荷魯斯之眼] 套用 MG背景動畫（clip_1） |
| Module | 荷魯斯之眼 |
| Label | 客戶端/前端 |
| Assignee | 前端 陳前端 |
| Status | In Progress |
| 相依關係 | blocked by → 上面的動效卡 |

兩張卡的狀態都要轉 Done，這一項動效才算真正完成——這是動效與前端唯一需要逐項對應的地方，原畫跟音效都不用這樣做。

### 範例3：音樂音效（整批交付，無 relation）

| 欄位 | 內容 |
|---|---|
| 標題 | [音效][荷魯斯之眼] basiscgame 主遊戲背景音樂（MG-BGM） |
| Module | 荷魯斯之眼 |
| Label | 音效與音樂 |
| Assignee | 音樂音效 林音效 |
| Status | Done |
| 內容 | 播放時機：進入主遊戲場景後立即播放，循環；Loop：是 |

音效清單全數完成後，整批交付前端套用，**不會**逐項開對應的前端工作事項。

### 範例4：企劃與數值、伺服器/後端、QA測試驗證（較粗顆粒度）

| Module | Label | 標題範例 | Assignee | Status |
|---|---|---|---|---|
| 荷魯斯之眼 | 企劃與數值 | [規格][荷魯斯之眼] 遊戲規格書 | PM+企劃 | Done |
| 荷魯斯之眼 | 企劃與數值 | [機率][荷魯斯之眼] RTP/賠付邏輯交付 | PM+企劃（代機率外包更新） | Done |
| 荷魯斯之眼 | 伺服器/後端 | [後端][荷魯斯之眼] 遊戲邏輯/API 實作 | 後端 | In Review |
| 荷魯斯之眼 | QA測試驗證 | [QA][荷魯斯之眼] 完整測試驗證（含RTP模擬） | QA | Todo |
