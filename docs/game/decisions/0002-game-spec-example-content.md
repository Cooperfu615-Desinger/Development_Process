## 考慮過的選項

### 內容來源

**選項 A:延續既有 QA/Plane 範例的做法,手寫一份簡化的示意規格書**
- 優點:篇幅可控,格式好對齊既有設計系統
- 缺點:失去真實規格書的數值密度與複雜度示範價值(既有兩份 Plane 範例、QA 範例都已經是「示意」等級,團隊真正需要的是看過一份「真實規格書長什麼樣」的參考)
- 結果:放棄——Cooper 直接提供了真實文件,沒有必要再手寫簡化版

**選項 B:直接採用 Cooper 提供的真實規格書全文(採用)**
- 優點:內容即戰力,團隊可直接參考真實規格的章節結構、數值precision、警語寫法(如 Special Bets 不保證中獎的官方原文引用)
- 缺點:內容量大(13個章節、多個精確數值表格),轉換過程有更高的數值謄寫錯誤風險
- 結果:採用,但需要額外的轉換保真度驗證步驟(見下)

### 轉換方式

**選項 A:手動逐段改寫成 HTML**
- 缺點:308行含精確賠付表/RTP數值的文件,人工謄寫數值出錯風險高,不符合 CLAUDE.md「涉及機率、賠付、金額的結論需附驗證方式」的精神
- 結果:放棄

**選項 B:用 Python `markdown`套件(v3.9,含 tables extension)做結構轉換,再手動修正已知的解析器限制,並做轉換前後數值比對驗證(採用)**
- 作法:
  1. 用 `markdown` 套件轉換 YAML front matter 之後的章節本文(表格、清單、粗體/斜體、code span 自動轉換正確)
  2. 手動修正 3 處已知的 parser 限制:(a) blockquote 內緊接粗體行、無空行分隔的清單不會被辨識為 `<ul>`(2 處手動改寫成 `.example`/`.warning` div);(b) blockquote 內巢狀 `*斜體 **粗體** 斜體*` 會被錯誤拆成 3 段獨立 `<em>`,遺失內層 `<strong>`(1 處手動修正巢狀標籤);(c) 2 處 2-space 縮排的巢狀清單被拉平,手動補回 `<ul>` 巢狀結構
  3. `~~刪除線~~` 語法(套件不支援)用 regex 轉成 `<del>`
  4. QA checklist 的 `- [ ]` 語法(套件不支援 GFM task list)用 regex 轉成既有站內慣例的 `<li>☐ ...</li>` 格式
  5. **驗證**:轉換前後分別用 regex 抓出所有數字 token(`\d[\d,.]*x?%?`),用 Counter 比對兩邊差集,確認轉換後沒有任何數值被遺漏、增加或竄改(唯一差異是新增的 `<h4>`/`<h5>` 標籤本身含有的數字「4」「5」,已排除)
- 結果:採用。此方式把「內容轉換保真度」的驗證從純人工檢查(容易漏看)改成程式化 diff,符合 CLAUDE.md「純人工推導不算驗證」的要求

### 標點符號轉換範圍

Cooper 先前對本檔其餘章節有明確指示「全部標點半形改全形」。本次新增內容的處理:
- 來源文件本身已大量使用全形中文標點(因為是給中文團隊看的規格書),半形殘留主要集中在:英文章節標題後綴括號(如 `(Changelog)`)、版本號/小數點/千分位逗號等技術性數字內容
- **決定**:只轉換「包裹英文參考詞的括號」(比照既有文件慣例,如 `Plane.io 狀態對應（Backlog / ...）`的先例),其餘一律保留原樣不做全文盲目轉換,理由是這份文件數值密度極高(賠付表、RTP百分比、倍數),盲目轉換半形句點/冒號有極高機率誤傷小數點、版本號、比例數字(如 `40/20/4`、`96.60%`、`2.5`)——上一輪標點轉換就曾意外破壞 `&lt;`/`&gt;` HTML entity 與多個 `onclick`/`style` 屬性(見 `~/.claude/logs/pitfalls.md` 2026-08-19 條目),本次選擇保守範圍以避免重蹈覆轍
