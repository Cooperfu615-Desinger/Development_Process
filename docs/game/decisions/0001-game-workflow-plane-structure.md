# 決策紀錄 0001:遊戲開發流程角色定義與 Plane.io 結構

- 日期:2026-08-12
- 決策者:Cooper
- 狀態:已採用(骨架方向確認,細節待補,見 SOP 第5節)

## 背景

平台流程 SOP 定案後,Cooper 要再整理一份博弈遊戲開發流程,兩者已拆到 `docs/platform/`、`docs/game/` 兩個獨立資料夾(見根層級決策 `docs/decisions/0001-docs-architecture-split.md`)。Cooper 說明角色配置(PM+企劃合一、機率外包、後端、美術原畫、美術動效、前端、音樂音效、QA)、流程依賴關係,並提供三份實際使用的 xlsx 清單(`巨亨麻將_原畫清單.xlsx`、`荷魯斯之眼_音樂音效清單.xlsx`、`荷魯斯之眼 動畫清單.xlsx`)與一張甘特圖作為時程參考。

## 考慮過的選項

### Plane.io 結構

**選項 A:比照平台流程,單一遊戲工作單(父工作項)+ 各單位子工作項**
- 優點:跟平台流程一致,容易理解
- 缺點:Cooper 明確說明實際做法不是這樣——七個單位是各自獨立的固定 Plane 專案(跨遊戲通用),不是掛在單一遊戲工作單底下的子工作項;原畫等單位一款遊戲就有百餘個逐項工作事項,套父工作項+子工作項的模式不符合實際規模與操作習慣
- 結果:放棄

**選項 B:七個固定跨遊戲專案,遊戲用標籤/週期區分,逐項工作事項 + relation 表示依賴**
- 優點:符合 Cooper 說明的實際運作方式與 xlsx 清單反映的顆粒度(原畫約120項/款、動效約69項/款、音效約31項/款)
- 缺點:結構比平台流程複雜,PM+企劃要同時追蹤七個專案裡屬於同一款遊戲的進度,管理負擔較高——但這正是 Cooper 一開始就提到的現況(PM+企劃比較多事情),SOP 只是如實反映,不是製造新問題
- 結果:採用

### 雙重驗收機制

從 `荷魯斯之眼 動畫清單.xlsx` 觀察到「製作完成」與「前端進度」兩個獨立勾選欄位,代表動效項目需經過「動效組完成」→「前端套用完成」兩關。Cooper 確認:動效與前端各自開一張對應的工作事項,用 Plane 關聯(relation)連結。原畫與音效清單則只有單一完成欄位,Cooper 確認這是有意設計——原畫→前端、音效→前端不做逐項雙重驗收(原畫前端自行抓整批進度;音效整批交付)。

放棄的方案:曾考慮讓原畫、音效也比照動效做逐項 relation 對應,但 Cooper 確認現況就是只有動效需要這樣做,不需要統一成同一套機制。

### 上線的歸屬

xlsx 清單與討論中未提及「上線」該歸在哪個 Plane 專案。決定歸在「企劃+機率」專案的最後一項,理由:PM+企劃是負責上線協調、對需求方回報的角色。此為技術性選擇(可逆、影響範圍限於本專案文件),已在 SOP 開放問題清單中註記待 Cooper 確認是否符合實際安排。

## 決定

- 角色定義、流程依賴關係、Plane 七專案結構、雙重驗收機制、機率/RTP驗證要求,詳見 `../SOP.md`
- 清單(xlsx)與 Plane 狀態的關係為人工雙軌(清單勾選 + Plane 手動同步更新),SOP 如實記錄現況,不預設要改變此做法
- 機率/RTP/賠付邏輯的驗證要求對應 CLAUDE.md 不可妥協項目2:後端或 QA 需做模擬驗證,不可僅信任外包商交付結果
