# 決策紀錄 0001:角色詞彙統一、Cycle彈性使用原則、吸收《產品開發流程.pdf》內容

- 日期:2026-08-15
- 決策者:Cooper
- 狀態:已採用

## 背景

比對報告 `docs/analysis/產品開發流程pdf比對報告.md` 列出5個需要 Cooper 確認的落差,才能把另一位PM整理的《產品開發流程.pdf》內容併入 `docs/core/SOP.md`。Cooper 逐項回覆後,本次據以修訂核心規範至 v0.2。

## 決定

### 1. 角色詞彙

不採用 PDF 的 FE主管/BE主管/SRE 獨立主管職稱。目前組織現況:**PM 與企劃是同一人**;技術面統稱「**技術組長**」,依專業各有一位,目前涵蓋美術、前端、後端、QA、SRE 五個領域。核心規範第2節角色表已更新反映此現況,技術規劃階段(第4節)的分工描述改用「前端(技術組長主導)」「後端(技術組長主導)」「SRE」這種表述,不使用「主管」。

### 2. Cycle(週期)的定位

保留 Cycle 概念,大方向一定要有週期,但週期怎麼用依實際專案性質調整,不是所有工作都套固定節奏:
- 遊戲開發:一款遊戲對應一個完整週期,從規格到上線期間不中途變動
- 平台小型變更(例如後台新增篩選功能):不需要走完整週期

此原則已寫入核心規範第7節「Plane 開立規則」的 Cycle 說明。

### 3. PDF 內容的性質與吸收範圍

Cooper 確認《產品開發流程.pdf》是建議性質(不是既有實際做法),因此比對報告第4節列出的6項「建議吸收」內容,全數採用,已併入核心規範 v0.2:
1. Bug/Hotfix 分級處理 playbook → 核心規範第9節新增小節
2. 規格完整性審查九面向 → 核心規範第8節新增小節
3. 需求變更四級分類(含緊急插單)→ 核心規範第11節需求變更規則改為四級表格
4. 角色參與速查矩陣 → 核心規範新增第6節
5. 需求探索技法(心智圖/功能地圖/競品分析/決策留痕)→ 核心規範第4節新增小節
6. 技術規劃三方分工細節 → 核心規範第4節新增小節(用語依決定1調整為技術組長,不用主管稱呼)

### 4. Plane/機率驗證/決策紀錄等既有內容

維持不變,PDF 內容是補充,不取代核心規範原有的 Plane規則、規格書模板、QA/客服表單、決策紀錄與 not_stated 紀律等章節。

### 5. 「沒有獨立專案經理」的組織假設

**不採用**。PDF 原文因為沒有獨立專案經理而特別設計 WBS 流程配套說明,但 Cooper 確認目前組織架構下 PM 本來就等於專案經理,這是既定分工模式而非需要特別聲明的限制或缺口,後續分工也會延續這個模式。核心規範不新增這條假設聲明。
