示範核心規範「Plane 開立規則」擴充文件底下的 QA 測試規範的實際填寫方式。QA 規則不分平台/遊戲,通用適用;遊戲類專案額外的機率/RTP模擬驗證要求,見遊戲的 Plane 使用範例。範例情境延續平台的「新增手機驗證功能」需求。

開發自檢 Checklist(填寫範例)

  • ☑ 正常流程符合規格書與驗收條件;必填、格式與邊界值完整
  • ☑ Loading、Empty、Success、Error、Disabled、網路/API 失敗與重複提交皆處理
  • ☑ 資料 CRUD、角色權限、敏感資料遮罩與輸入驗證正確(驗證碼不寫入一般 Log)
  • ☑ Code Review、受影響流程回歸、必要單元/整合測試已完成
  • ☐ 埋點、Log、錯誤追蹤、監控、Migration、Feature Flag、回滾資訊已確認 ← 埋點尚未加,已回報開發組長

工程應在自檢全數勾選、且未勾選項目有明確後續處理前,才把版本交給 QA。

Bug/Hotfix 分級處理範例(P0 情境示範)

假設同一支手機驗證功能上線後,正式環境出現「簡訊發送 API 大量逾時,導致所有會員都無法完成驗證」:

  1. 客服/監控回報 → PM 判定為 P0 致命(核心流程完全不可用)
  2. SRE 先止血:關閉手機驗證功能的 Feature Flag,暫時允許會員略過驗證完成登入
  3. 後端依 Log 排查根因(簡訊供應商逾時,非本次程式改動造成)
  4. 修復(切換備援簡訊供應商)後,補上對應測試(模擬供應商逾時情境)
  5. QA 在測試站複現並驗證修復,執行 TC-MEMBER-001~006 回歸
  6. 因應急性,先恢復服務(重新開啟 Feature Flag),正式測試報告與文件於服務恢復後補齊
  7. 事後復盤:根因為單一簡訊供應商依賴,後續應追蹤是否需要多供應商備援(列入待辦清單,不究責)
