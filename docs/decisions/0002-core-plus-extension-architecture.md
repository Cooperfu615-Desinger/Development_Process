# 決策紀錄 0002(架構層級):核心規範 + 領域擴充架構,整合 SOP工作流程中心.html

- 日期:2026-08-15
- 決策者:Cooper
- 狀態:已採用(核心規範正文已完成,平台/遊戲擴充文件精簡與統一 HTML 重新產生為後續步驟)

## 背景

Cooper 在 `docs/` 下新增一份 `SOP工作流程中心.html`——一份涵蓋 PM工作流程、遊戲開發流程、Plane開立規則、QA測試檢測表、客服回應表、規格書撰寫規範六大主題的單頁應用式文件。其中「遊戲開發流程」章節與我們已完成的 `docs/game/SOP.md` 高度重疊(同樣的依賴關係、Plane七專案結構、雙重驗收機制),「規格書撰寫規範」章節與 `docs/platform/templates/spec-template.md` 結構相近;但其餘四個章節(PM工作流程、Plane開立規則、QA、客服)是我們完全沒碰過的新內容。

Cooper 希望把平台、遊戲、這份新 HTML 三邊內容整合成「不分平台/遊戲的共同規範,後續任何專案類型都能沿用」。

## 考慮過的選項

### 選項 A:直接以新 HTML 為主體,把平台/遊戲內容塞進對應章節
- 優點:不用重新設計架構,新 HTML 的六個章節本來就分好類別
- 缺點:新 HTML 是手寫 HTML,沒有版控友善的 markdown 來源、沒有決策紀錄串接、沒有 not_stated 慣例;而且它已經把「PM工作流程」跟「遊戲開發流程」當兩個平行章節處理,沒有真正抽出「哪些是任何專案都共用、哪些是遊戲特有」的界線——這樣以後新增第三種專案類型時還是要整章複製貼上
- 結果:放棄

### 選項 B:核心規範(domain-agnostic)+ 領域擴充文件(只寫差異),核心規範用 Markdown 撰寫,單頁 HTML 作為重新產生的閱讀層
- 優點:延續本專案已建立的 Markdown-as-source-of-truth 慣例(可版控、可決策紀錄、可 not_stated 標記);新增專案類型時只需寫「跟核心不同的地方」,不用整套複製;新 HTML 的六個章節裡,「PM工作流程/Plane規則/QA規則/客服規則/規格書規範」本來就寫得夠通用,適合直接收進核心,「遊戲開發流程」則收進 `docs/game/` 當領域擴充
- 缺點:需要额外的架構設計與內容拆分工作,不能整段複製貼上
- 結果:採用

## 決定

### 1. 架構

`docs/core/SOP.md` 為所有專案類型共用的核心規範,涵蓋:角色與組長品質把關機制、需求分流與流程深度、完整流程階段與DoR/DoD、Plane開立規則(欄位/卡片/Priority,不含拓撲)、規格書撰寫規範、QA測試檢測表規則、客服回應規則、管理工具(RACI/風險登錄表/需求變更規則)、Figma畫面狀態標記規則、決策紀錄與not_stated紀律。`docs/platform/SOP.md`、`docs/game/SOP.md` 精簡為只寫各自的差異(主要是 Plane 拓撲結構與領域特有的驗證要求)。

### 2. Plane 結構衝突的解法

不強行統一 Plane 拓撲。核心規範只定義欄位、卡片必填規則、Priority定義等通用層面;「要用單一工作單+子工作項,還是七個固定跨遊戲專案」這種拓撲層級的決定,交給各領域擴充文件說明現況,細節留給開發團隊自行調整與拍板。核心規範裡雖然列了一個「Cycle→Project→Module→父Issue→Sub-issue」的參考層級,但明確註記這只是參考,不是要團隊改成這樣。

### 3. Plane 定位一致性

Cooper 確認:遊戲流程裡的 xlsx 清單,本質上就是新 HTML 所說的「連結文件」——Plane 記狀態與追蹤進度,連結文件(不論是 Figma、PRD、或 xlsx 清單)記實際內容,兩者不衝突,不需要為了「Plane 是唯一事實來源」這句話去改變遊戲現況的人工雙軌做法。

### 4. 內容性質標注:哪些是既有做法、哪些是新規範

跟 Cooper 逐項確認新 HTML 裡的內容:
- **Figma 畫面狀態標記規則**(五色狀態燈):既有實際做法,直接收進核心規範第11節
- **其餘章節**(三種流程深度分級、0-11步驟分流圖、DoR/DoD、RACI表、風險登錄表、Plane的Type/Status/Label/Priority/Module豐富欄位分類、QA測試檢測表、客服回應表):Cooper 確認「大部分都是新建議,目前還沒這麼正式」——即這次整合是**把這些內容正式立為公司新標準**,不是記錄既有現況。核心規範開頭明確標注這個性質,避免之後有人誤以為這些規則早就在跑。

放棄的方案:曾考慮把「既有 vs 新規範」的區分放進開放問題清單、要求逐條後續確認,但這樣核心規範會充滿不確定性標記,不利於作為團隊可以直接依循的文件。改為在核心規範開頭一次性聲明「除第11節外皆為新規範」,細部的未決數值(如發布核准人、SLA時限、工作量上限)仍個別列在開放問題清單。
