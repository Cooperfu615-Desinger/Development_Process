01 · PM 工作流程

PM 工作流程

適用於平台功能、新增、優化、BUG、技術債與維運。流程的目標不是多開會，而是讓不同 PM 都能快速釐清問題、和技術有效協作，並留下可追溯的決策。

三種流程深度：快速流程（P0／P1、低風險修正）、標準流程（一般需求）、完整流程（新專案、重大改版、金流／資安／高風險變更）。不論流程深度，需求原話、證據、負責人與發布紀錄都不可省略。

每一步的交付與完成門檻

閱讀方式：左側是流程步驟；中間是主要責任人與要交付的內容；右側綠色框是「符合才能往下走」的關卡。

0
PM需求登錄與證據
要做什麼／產出什麼保留需求原話、提出人、時間、來源、截圖／錄影／紀錄檔／數據。
可往下走的條件第三人可理解誰在何情境提出何事，且證據可追溯。
1–2
PM分級與問題分析
要做什麼／產出什麼分開記錄任務類型、影響嚴重度與處理優先級；定義使用者、痛點、範圍、成功指標。優化要有基準值；BUG 要有重現與替代方案。
可往下走的條件能說清楚問題與成功條件，不只是重述提出者的解法。
3–4
PM＋設計／組長／QA規格、設計與技術評審
要做什麼／產出什麼完成規格書、Figma／原型、技術文件與驗收條件；記錄方案、風險、估時、相依、未決事項、決策人與期限。
可往下走的條件所有阻塞開發的問題已決定；文件版本一致。
5
PM＋技術組長拆分、估時與排程
要做什麼／產出什麼組長拆分子任務並回報開始與預計送測日；PM 設定開發週期、主要負責人、審核人、期限與相依關係。
可往下走的條件符合開發準備完成條件（DoR）。
6–8
工程／組長／QA開發、組內審查、測試
要做什麼／產出什麼實作、程式碼審查、組長審查、自檢、部署測試站、QA 測試、缺陷修復與回歸。
可往下走的條件P0／P1 缺陷為零；必測案例完成；測試結論明確。
9–11
PM／主管／SRE／客服驗收、發布、回顧與迭代
要做什麼／產出什麼UAT、發布核准、回滾方案、正式發布、監控、客服通知、KPI／事故回顧與後續任務。
可結案條件符合完成條件（DoD），觀察結論與後續責任人已記錄。

各階段注意事項

接需求時

不要先答應時程或解法。先記錄客戶／提出人的原話與證據；PM 的分析請另寫，避免混淆事實與推測。

寫規格時

每個流程要寫成功、失敗、無資料、載入、權限不足與重複操作的結果。不要只寫「系統應正常運作」。

開發中

需求變更不可只留在群組訊息；應更新 PRD 與 Plane，並重新確認範圍、工時與發布風險。

送測前

工程先完成自檢，不要把「工程尚未測過」的版本交給 QA。QA 是品質驗證，不是代替開發除錯。

發布前

確認測試版本、正式版本、Migration、Feature Flag 與回滾方案。沒有回滾方式，不應發布高風險變更。

上線後

功能發布不等於結案。PM 要看 KPI，工程／SRE 要看錯誤率、延遲與告警，客服要收集回饋。

常見失敗方式：把 BUG、優化放進狀態欄；一張卡有多位「主要」負責人；沒有驗收標準就進開發；主管口頭說 OK 但沒有紀錄；上線後沒有指定觀察人。以上都會讓問題無法追溯。

導入前仍需公司確認的規則

項目建議規則為什麼需要確認
決策時限需求、設計、技術、主管驗收各自設定回覆時限；逾期由 PM 升級處理。避免任務停在「等回覆」卻沒有責任人。
例會節奏每週需求／排程會、開發阻塞同步、發布前檢查、上線後回顧。讓跨部門問題在固定節奏中被發現，而非臨時救火。
風險登錄重大任務需記錄風險、機率、影響、應對方案與責任人。避免只記「有風險」卻沒有後續行動。
文件版本PRD、Figma、技術文件都要有版本、日期、作者與核准狀態。避免工程、QA、主管看的是不同版本。

需求變更規則

不影響範圍、時程與驗收的文字／小型介面調整：PM 更新規格與設計紀錄即可。影響 API、資料、權限、工時、發布日或驗收條件的變更：必須回到技術評審，由組長重新估時、PM 更新 Plane 與需求方決策。新增功能一律另開工作卡，不直接塞進進行中的任務。

角色邊界

PM

決定問題、優先級、商業範圍、驗收與協調；不單方面指定技術實作。

技術組長

參與技術訪談，確認方案、拆分工作、指派成員、回報開始與預計送測日；審核組內產出品質。

工程／SRE

依組長分派執行架構與實作；規格不清時必須回問，不可自行猜測商業邏輯。

設計／QA

設計負責體驗解法與狀態；QA 負責測試策略與品質判定，主管負責重大風險取捨。

組長審核與交接機制

關卡組長責任PM 責任Plane 紀錄
技術訪談確認團隊是否理解需求、提出實作方案／風險／依賴，並回報可行的起訖時間。確認範圍與驗收條件；未定案事項指定決策人與期限。技術訪談結論、估時、風險與相依任務。
工作分派拆分前端、後端、SRE、設計、QA 子任務；每項指定實作者與審核人。確認任務符合本次範圍、Cycle 與交付日期。子任務的主要負責人、組長審核人、開始／截止日。
組內審查檢查品質、規格符合度、測試／文件是否完整；不符合就退回修改。協助排除跨組阻塞，不代替組長做技術品質判定。任務先進「審查中（In Review）」；組長核准後才可完成。
時程異常預期延遲時主動告知 PM，說明原因、影響與替代方案。與需求方協調時程、範圍或優先順序，並更新決策。更新阻塞原因、新日期、影響任務與決策紀錄。
重要：組長不是只在最後看成果。組長必須在「規格理解、任務拆分、組內審查、時程異常」四個關卡留下紀錄。若同一人同時是組長與實作者，仍需由另一位指定審核人或跨組審核人完成品質確認。

開始與完成條件（DoR / DoD）

開發準備完成（DoR）完成並可結案（DoD）
  • 問題、目標、範圍／非範圍已定義。
  • 主要負責人、優先級、開發週期、期限已設定。
  • 驗收條件、設計與技術資訊足以開發。
  • 相依與風險已揭露，QA 知道測試範圍。
  • 程式碼審查（Code Review）、自檢、QA、必要 UAT 通過。
  • 驗收條件、文件、埋點、紀錄檔（Log）、監控已更新。
  • 發版紀錄、回滾、上線觀察已完成。
  • 已知風險已有後續任務與責任人。

文件範例演示

PRD／規格書範例：新增手機驗證
一、問題：未驗證手機的帳號容易造成聯絡失敗與風險操作。
二、目標：會員可完成手機驗證；驗證成功率達 90% 以上。
三、本次範圍：個人資料頁的手機輸入、簡訊驗證碼、成功／失敗提示。
四、不包含：變更手機門號後的人工審核流程。
五、操作規則：輸入合法手機號碼後可發送驗證碼；60 秒內不可重複發送；連續錯誤 5 次後暫停 10 分鐘。
六、畫面狀態：初始、發送中、倒數、驗證成功、格式錯誤、驗證碼錯誤、服務失敗、權限不足。
七、驗收標準：會員完成驗證後，資料庫驗證狀態更新；重新登入後狀態仍保留；錯誤提示符合設計稿。
技術文件範例：手機驗證 API
項目內容
APIPOST /api/v1/phone-verifications
權限已登入會員；僅可驗證自己的手機號碼。
請求欄位phone（必填，字串，符合手機格式）
成功回應回傳驗證工作階段 ID、剩餘秒數與過期時間。
錯誤處理格式錯誤、超過發送次數、簡訊服務失敗、權限不足。
安全與限制每帳號／手機號碼限流；不得在 Log 寫入完整驗證碼；驗證碼雜湊保存。
監控發送成功率、驗證成功率、第三方失敗率、限流觸發量。

UI 畫面狀態標記規則

每個有異動的 Figma 畫面或設計交付頁面，應在標題前加上狀態標記。這是「畫面交接狀態」，不是 Plane 任務狀態；目的是讓設計與前端一眼判斷目前是否需要開始工作。

首頁－開發完成

意思：前端實作已與設計稿相符，設計與前端都完成。若沒有新異動，兩方都不需再處理。

首頁－修改中

意思：設計正在修改，或需求、畫面內容仍有錯誤。前端暫時不需動工，避免做出即將被推翻的版本。

首頁－待討論

意思：修改需求尚未定案。PM 應安排討論、留下決策紀錄；設計與前端都不需動工。

首頁－待 RD 處理 設計完成

意思：設計已完成且可交付前端；前端需要開始製作。若有 API、資料或技術疑問，先在 Plane／技術訪談中確認。

本次異動畫面

意思：用於標示本次版本實際有調整的畫面，避免測試與前端誤以為整份設計稿都需要重做。

使用規則：狀態一變，設計師需同步更新 Figma 畫面標題與 Plane 卡片連結；PM 需確認「待討論」有決策人與期限；只有標示「待 RD 處理」的畫面可以交給前端開發。若前端已開始後設計再改動，必須改回「修改中」並在 Plane 記錄影響與是否需重新估時。
02 · 遊戲開發流程

遊戲開發流程

適用於含玩法規則、機率、RTP、賠付邏輯的遊戲專案。它與一般平台功能流程不同：多條素材與技術線並行，且機率／賠付結果必須以可重現的模擬或統計驗證。

不可妥協：凡涉及機率、RTP、賠付、派彩或金額的「可行／通過／可上線」結論，必須附驗證方式與結果；不可僅依人工推導或外包交付宣稱通過。

單一遊戲開發依賴關係

年度規劃／需求確認 → 遊戲規格書
                         ├─ 機率／RTP／賠付邏輯（外包）→ 後端
                         └─ 原畫 → 動效 ─┬→ 音樂音效
                                           └→ 前端逐項套用
後端 API ＋ 原畫 ＋ 動效 ＋ 音效 → 前端最終整合 → 前端自測 → QA（含 RTP 模擬）→ 驗收 → 上線

遊戲專案角色與交接

角色輸入產出離開條件
PM＋企劃年度計畫、需求方確認玩法規則、規格書、時程、上線協調規格定版，所有單位拿到可執行輸入。
機率／RTP（外包）遊戲規格機率、RTP、賠付邏輯與計算假設後端能依正式版本實作，變更有版號。
原畫規格書逐項靜態美術素材與清單清單完成並經組長品質審核。
動效原畫素材逐項動效；每項關聯一張前端套用任務動效完成且前端套用完成，雙方狀態一致。
音樂音效動效逐項音效，整批交付前端清單完成、交付版本明確。
後端機率邏輯遊戲後端邏輯、API、模擬工具／紀錄自測通過，API 可供前端串接。
前端原畫、動效、音效、API完整可玩的整合版本自測通過，素材關聯任務完成。
QA整合版、規格、機率模型功能／回歸／RTP 模擬測試報告阻塞缺陷歸零或風險已書面接受。

遊戲各技術組長的責任

組長規格階段製作階段交付前審核
原畫組長確認素材清單、視覺風格、規格與交付格式。分派素材項目、維護清單進度。確認素材完整、命名／尺寸／格式正確，再交前端。
動效組長確認動效觸發、循環、節奏與對應原畫。分派動效項目，與前端確認 Relation 對應。確認動畫品質、效能與前端套用條件。
音樂音效組長確認音效觸發點、音量規範與素材格式。分派音樂／音效清單。確認檔案完整、音量／格式符合規格後整批交付。
前端組長確認畫面、素材、API、效能與裝置相容方案。分派整合、動效套用、效能優化與自測任務。確認遊戲完整可玩、素材清單一致並可送 QA。
後端組長確認機率模型、賠付規則、資料與 API 實作方案。分派邏輯、API、模擬與監控任務。確認模型版本、模擬結果、API 文件與自測完成。
QA 組長確認測試範圍、RTP 驗證策略、裝置矩陣與測試資料。分派功能、回歸、模擬與發布驗證。審核測試報告、缺陷風險與發布建議。

遊戲專案的完整階段與交付物

0
PM＋企劃年度／季度規劃
要完成什麼確認遊戲數量、題材、目標市場、玩法方向、上線檔期、預估資源與商業目標；先排除法規、授權、平台限制。
放行條件需求方確認優先順序與檔期；每款遊戲有初步負責人與時程假設。
1
PM＋企劃遊戲規格
要完成什麼玩法循環、投注／獎勵規則、符號／關卡、介面流程、音效觸發、素材清單、RTP／賠付需求與驗收方式。
放行條件規格版本定版；每個規則可被機率、前後端、QA 分別理解與驗證。
2
機率＋美術並行製作
要完成什麼機率外包交付模型、假設與賠付表；原畫建立素材清單、動效依原畫逐項製作、音效依動效製作。
放行條件機率版本可供後端實作；素材有檔名、版本、格式與組長審核紀錄。
3
後端＋前端實作與整合
要完成什麼後端實作遊戲邏輯與 API；前端套用原畫、動效、音效並串接 API。動效與前端套用需逐項關聯。
放行條件完整遊戲可玩；前端自測與素材對照清單完成。
4
QA＋PM驗證、發布、營運
要完成什麼功能、回歸、跨裝置、效能、RTP／賠付模擬、UAT、發布紀錄、版本回滾與上線監控。
放行條件測試報告通過；RTP 結果符合標準；發布與回滾責任人明確。

遊戲專案在 Plane 的開立方式

遊戲工作不建議只用一張大卡追蹤。可採七個固定跨遊戲 Project，並以「遊戲名稱」標籤、版本與 Cycle 區分同時進行的遊戲；每一個交付物都必須能回到同一款遊戲的規格版本。

Plane Project任務拆分方式交接與驗收
企劃＋機率規格書、機率／RTP／賠付表、上線協調。機率版本交給後端；變更須回寫規格與關聯任務。
原畫每個靜態素材一張工作項或素材清單項。組長審核後完成；前端依整批／清單套用。
動效每個動效一張工作項。與前端「套用動效」工作項建立 Relation，兩邊都完成才算完成。
音樂音效依音效清單逐項建立。整批交付前端；明確記錄素材版本。
後端依遊戲邏輯、API、模擬工具拆分。自測、API 文件與模擬結果交付前端／QA。
前端遊戲容器、素材套用、API 串接、效能優化。自測通過；動效關聯工作項與素材清單一致。
QA功能、回歸、RTP 模擬、跨裝置與發布驗證。產出測試報告、缺陷清單與發布建議。

遊戲規格書最低內容

玩法與數學規則

投注範圍、機率表、RTP、賠付表、符號權重、獎池、免費遊戲、加成與邊界條件。

畫面與素材

畫面流程、UI 狀態、素材清單、檔名、尺寸、格式、動效觸發與音效對照表。

系統與資料

API、遊戲局號、投注／派彩紀錄、錯誤碼、斷線重連、重播或交易追溯規則。

測試與發布

RTP 模擬方式與樣本數、測試環境、支援裝置、Feature Flag、監控與回滾條件。

遊戲專屬品質與發布關卡

  • 版本控管：規格、賠付表、機率模型、素材包、API 與測試報告都必須標示遊戲名稱與版本。
  • 雙重驗收：動效任務需同時完成「動效組產出」及「前端套用」；兩張 Plane 任務用關聯（Relation）互連。
  • RTP 驗證：記錄樣本數、隨機種子／環境、期望 RTP、實測 RTP、允許誤差、檢定／計算方法及執行人。
  • 組長審核：各單位的工作在「審查中」（In Review）由組長品質確認後，才能進「完成」（Done）。
  • 上線：需包含遊戲版本、賠付模型版本、功能開關（Feature Flag）、回滾遊戲版本與上線後異常監控。
遊戲開發特別注意：機率模型與程式實作必須是同一版本；改玩法、賠付表、符號權重或獎池規則時，需重新確認機率、重新跑模擬、重新測試，不可只修改畫面或文案後直接上線。

03 · Plane

Plane 開立規則

用狀態管理生命週期；用 Type 與 Label 管理任務本質。每張卡都要有一位主要責任人與可追溯的完成條件。

欄位定位

欄位用途例子
Type任務本質，只選一個Feature、Improvement、Bug、Tech Debt、Ops
Status任務目前處於哪個生命週期開發中、QA 測試中、待發布
Label可複選的篩選屬性frontend、backend、sre、security、hotfix
Priority處理先後順序P0～P3
Module所屬產品功能域會員、訂單、金流、後台

建議層級與狀態

Cycle（週期）
└─ Project（產品目標／版本）
   └─ Module（功能域）
      └─ 父 Issue（交付目標）
         └─ Sub-issue（設計、前端、後端、QA、SRE）
需求已接收→需求分析／規格中→待安排→已排定→開發中→組內審查→自檢／測試站→QA→驗收→待發布→已發布／觀察→已結案

每張卡必填

  • 標題：[Type][Module] 動作＋目標
  • 單一 Assignee、開始日、截止日、Cycle、Project、Module。
  • Type、Priority、Status、必要 Labels 與相依關係。
  • 組長審核人（Reviewer）：每張開發、設計、QA、SRE 子任務必填；實作者不可自行跳過審核直接標示完成。
  • PRD、Figma／原型、技術文件、PR／GitHub、測試案例連結。
  • Feature／Improvement 有驗收條件；Bug 有重現步驟與修復驗證條件。
組長的 Plane 流程：待開始 → 進行中 → 審查中（In Review）→ 完成。若審核不通過，組長應退回「進行中」並留下具體修改原因；不可用聊天訊息取代審核紀錄。

驗收條件：
- 使用者可在手機完成付款流程。
- 欄位驗證失敗時顯示明確提示。
- 付款成功事件可被埋點追蹤。

Priority 定義

等級定義處理原則
P0 Blocker服務中斷、資安、資料遺失、金流異常立即處理、事後 RCA
P1 Critical核心流程無法完成優先排入當前 Cycle
P2 Major一般功能、重要優化、有替代方案 BUG依 Roadmap 排程
P3 Minor低影響改善、文案／視覺調整放入 Backlog 定期整理

Plane 導入時還要設定的項目

  • 權限：誰能改優先級、關閉任務、改截止日、建立／刪除標籤與調整工作流程。
  • 工作量限制：每人同時「開發中」的任務上限；超過上限需先協調，不可持續插單。
  • 逾期處理：截止日前多久提醒、逾期後由誰更新原因與新日期。
  • 封存規則：已結案任務何時封存、取消任務需保留什麼原因、重複需求如何合併。
  • 儀表板：至少追蹤 Cycle 完成率、逾期任務、阻塞任務、缺陷趨勢與發布清單。
Plane 管理規則（導入版）
  • 父子同步：任何子任務未完成或被阻塞時，父任務不可標示「已結案」。
  • 逾期更新：主要負責人在預期延遲時更新原因、新日期與影響；技術組長確認後通知 PM。
  • 插單：P0／P1 以外的需求不可直接插入當前 Cycle；PM 與組長需明確記錄被延後的任務。
  • 取消／合併：取消卡保留原因；重複需求使用關聯或合併方式連到主卡，不刪除歷史。
  • 權限與工作量上限：由 Workspace 管理者與各組長依實際人力定案後設定；未定案前不得用系統自動化強制關卡。

測試制度還需要補的項目

環境與測試資料

定義測試站用途、資料重置方式、測試帳號權限與個資遮罩規則；不可使用未授權的正式個資測試。

裝置矩陣

列出公司承諾支援的瀏覽器、手機系統、螢幕尺寸與 App 版本；QA 才能有一致的相容性範圍。

自動化策略

先挑登入、付款、核心交易、權限、主要 API 等高風險回歸案例，訂定哪些案例必須自動化。

缺陷嚴重度

分開定義「嚴重度」與「優先級」：前者是影響程度，後者是商業處理順序，兩者不能混為一談。

測試環境與缺陷分級規則

項目規則
測試資料使用指定測試帳號與去識別資料；不得複製或展示未授權的正式個資。需要資料重置時，指定資料責任人與時間。
環境版本每次測試紀錄必須寫測試站網址、發布版本／Commit、Feature Flag 狀態、第三方沙盒狀態與測試日期。

自動化候選登入、權限、付款／金額、核心交易、重要 API 與高頻回歸流程優先；每個 Cycle 檢討新增候選案例。

06 · 規格書

規格書撰寫規範與範例

規格書是企劃、PM、設計、技術組長與 QA 的共同依據。它定義使用者與商業規則；API、資料庫、部署、監控與回滾由技術文件定義。

撰寫原則：先寫問題，再寫解法；「做什麼」與「不做什麼」必須同時存在；每條驗收條件都要可實作、可測試、可追溯。

正式規格書章節

1
版本歷程每次修改必更新
內容版本、日期、修改內容、修改人；重大決策需連結 Plane 或決策紀錄。
要求團隊只能依最新「已拍板」版本開發。
2
需求背景與目的先說明問題
內容需求來源、目標使用者、痛點、商業目標與成功指標。
要求能說明為何做，而不只是描述想做的畫面。
3
範圍邊界做什麼／不做什麼
內容本次功能、明確排除事項、相依功能與後續版本規劃。
要求不做事項不能用「視情況」或「之後再說」描述。
4
流程與 UI使用者如何操作
內容流程圖、Figma／Wireframe、畫面與狀態：正常、載入、無資料、錯誤、無權限、停用、重複提交。
要求設計完成前不可標示「待 RD 處理」。
5
業務欄位與規則不是技術資料庫設計
內容欄位名稱、使用者可見規則、必填、格式、權限、通知、例外與防呆。
要求資料表、API、錯誤碼與 Migration 交由技術文件定義。
6
影響與驗收QA 可直接使用
內容金額／派彩／餘額、權限、個資、外部服務、埋點、客服與報表影響；可勾選驗收條件。
要求每條驗收條件能對應至少一個 QA 測試案例。
7
需求會議與決策組長確認
內容會議日期、參與者、組長確認的工作細項、未決問題、決策人與期限、會後調整。
要求阻塞問題未定案時不可排入開發週期。

填寫範例：新增手機驗證

需求背景與目的

部分會員未驗證手機，造成通知無法送達並增加帳號風險。讓已登入會員完成驗證；目標為驗證成功率達 90% 以上。

範圍

包含手機輸入、發送驗證碼、驗證成功／失敗提示與狀態保存。不包含變更手機後的人工審核與海外簡訊供應商切換。

驗收條件
  • 輸入合法手機號碼後可收到驗證碼。
  • 60 秒內重複發送不會再送簡訊，並顯示倒數。
  • 驗證成功後狀態保存；重新登入後仍為已驗證。
  • 錯誤、過期與服務失敗顯示明確提示；驗證碼與完整手機號碼不寫入一般 Log。
送需求會議前：確認 Plane 連結、版本、範圍、流程、UI 狀態、影響評估、驗收條件與未決問題完整。需求會議需有相關技術組長與 QA 組長；會後結論必須回寫規格書與 Plane。
