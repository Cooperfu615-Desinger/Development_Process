# 比對報告:《產品開發流程.pdf》vs 現有規範(docs/core + docs/platform + docs/game)

- 日期:2026-08-15
- 來源文件:`~/Downloads/產品開發流程.pdf`(19頁,另一位PM獨立整理,未參考本專案文件或 `docs/SOP工作流程中心.html`)
- 比對對象:`docs/core/SOP.md`(核心規範)、`docs/platform/SOP.md`、`docs/game/SOP.md`

## 1. 這份 PDF 是什麼

一份聚焦在「產品經理視角」的開發流程文件,涵蓋:
1. 整體開發流程總覽(7大階段)
2. 新產品/大型新模組的完整10階段流程,每階段列出主要負責人、參與人、負責內容、主要產出
3. WBS 與時程掌控原則
4. 角色何時加入、主要做什麼(角色×階段對照表)
5. 六個關鍵協作點(需求/規格檢查、設計評審、技術評審、WBS/時程確認、開發同步、發布確認)
6. 既有產品的功能更新(Update)流程
7. Bug修復與Hotfix流程(依P0-P3分級)
8. 需求變更、插單與時程調整規則
9. 整體角色參與速查矩陣

角色設定:PM、Design、FE、BE、QA、SRE、FE主管、BE主管——**沒有獨立的「企劃」角色**,也**沒有提到 Plane.io 或任何專案管理工具**,文件明確說明「因目前沒有獨立的專案經理,由PM承擔WBS整合工作」。

## 2. 整體評估:互補大於衝突

兩份文件的詳細程度剛好落在不同的地方:

- **這份 PDF 在「需求探索 → 產品邊界確認 → 功能Mapping → 規格形成 → 設計 → 技術規劃」這段前期流程寫得比我們的核心規範細很多**——有心智圖/功能地圖技法、競品分析、跟老闆/提案人的範圍拍板機制、九面向規格完整性審查、技術規劃階段 FE主管/BE主管/SRE 三方各自的具體產出。
- **我們的核心規範在操作工具層(Plane欄位規則、QA表單、客服流程、規格書撰寫模板、DoR/DoD、RACI、風險登錄表、Figma狀態燈、決策紀錄與not_stated紀律)寫得完整,這份PDF完全沒有涉及**。

沒有發現方向性的衝突(兩者對「需求→規格→設計→開發→測試→發布→維運」的整體流程認知一致),主要是顆粒度跟涵蓋範圍不同。

## 4. 建議吸收進核心規範的內容(優先順序由高到低)

1. **Bug/Hotfix 分級 playbook**——目前核心規範只有 Priority 定義,沒有「P0該怎麼做、P1該怎麼做」的具體指引,這份PDF的版本可以直接補進核心規範第8節(QA測試檢測表開立規則)或獨立成新的一節
2. **規格完整性九面向檢查清單**——比核心規範第5節現有的六項更完整,建議取代或補充
3. **需求變更四級分類(補上「緊急插單」)**——核心規範第10節需求變更規則建議擴充成四級
4. **角色×階段速查矩陣**——建議在核心規範新增一節或附錄,提供這種一眼看懂的格式
5. **需求探索階段的心智圖/功能地圖技法、決策留痕機制**——建議補進核心規範第2-4節或規格書模板前面,強化「需求怎麼探索」這段(目前核心規範第4節步驟0-2寫得比較抽象)
6. **技術規劃 FE主管/BE主管/SRE 三方分工細節**——建議補進核心規範第2節角色定義或第4節技術評審步驟

## 5. 需要 Cooper 確認的落差

1. **角色詞彙不一致**:這份 PDF 沒有「企劃」這個角色,PM 身兼企劃工作;還多了 SRE、FE主管/BE主管這種我們核心規範沒有明確拆出來的角色。要統一角色詞彙(核心規範改成也拆 FE主管/BE主管/SRE),還是保留現有的通用角色表、只在說明文字裡帶到這些細分角色?
2. **「不以固定Sprint週期為前提」**:這份 PDF 在「開發同步」協作點明確寫「不以固定Sprint週期為前提」,但我們核心規範 Plane 章節用了「Cycle(週期)」的概念(第6節建議層級)。這是否代表團隊實際上沒有固定開發週期?如果是,核心規範第6節的措辭要調整。
3. **這份 PDF 的內容性質**:是這位PM團隊已經在跑的實際流程,還是也是這次要新建立的建議規範?這會影響要不要跟核心規範一樣標注「新規範,尚未正式導入」。
4. **這份 PDF 完全沒提到 Plane.io、機率/金流驗證要求、決策紀錄慣例、not_stated紀律**——確認這些是保留我們核心規範既有的部分,PDF 內容當作前段流程的補充,而不是取代。
5. **「沒有獨立專案經理」的組織假設**——這份PDF明確寫出這個限制並據此設計WBS流程(PM整合但不自己估算所有工時)。我們的核心規範沒有明確聲明這個假設,但實務上(平台/遊戲SOP都是PM或PM+企劃身兼多工)看起來現況相符——建議在核心規範裡也明確寫出這個組織假設,而不是含蓄帶過。

## 6. 建議下一步

不建議整份 PDF 直接貼進核心規範,而是依第4節列的6個項目,個別评估怎麼併入核心規範對應章節(部分是新增段落、部分是取代現有較簡略的版本)。建議順序:先處理第5節的5個確認點(尤其角色詞彙統一,這會影響其他所有併入動作怎麼寫),確認後再動手改 `docs/core/SOP.md`。
