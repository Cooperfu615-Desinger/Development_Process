# 決策紀錄 0003:時程落差處理方式、Plane.io 邊界、驗收簽核方式

- 日期:2026-08-11
- 決策者:Cooper
- 狀態:已採用

## 背景

決策0002遺留三個開放問題待決定:時程追蹤與落差升級機制(SOP 4.1)、Plane.io 是否有自訂欄位可標記金流/粗估區間、驗收簽核的具體形式。另外規格文件標準化模板的處理順序也一併確認。

## 決定

### 1. 時程落差處理機制(SOP 4.1)

不採用原本列出的固定門檻/預警/里程碑三選項中任何一個量化規則。改為:**PM 持續在 Plane 上追蹤進度,一旦預期delay,由 PM 直接與需求方協調(調整時程、範圍或優先順序),協調可在開發過程中隨時發生,不限定檢查點**。理由:落差處理仰賴 PM 對需求方關係與情境的判斷,不適合用死規則取代。

放棄的方案:到期預警制(SOP 4.1原選項A)、進度里程碑回報制(原選項B)、固定百分比/天數門檻升級制(原選項C)——三者皆因「想保留彈性給PM判斷,而非自動化規則」而不採用。

### 2. Plane.io 的角色邊界(SOP 4.4,新增)

確認 Plane.io 沒有自訂欄位功能。Plane.io 在流程中只做兩件事:確認有哪些工作項、追蹤進度到哪裡。除此之外的內容管理(規格書、測試報告等實質產出的撰寫與存放)交由各組組長自行處理,SOP 不強制規定工具或存放位置,只要求負責人/起訖時間/狀態要反映在 Plane 上。

放棄的方案:原本設計中部分描述要求「產出物填寫於 Plane 工作項內容/留言」,已在 SOP 全文淡化為「基本追蹤資訊反映於Plane,實質內容由各組自理」。

### 3. 驗收簽核方式(SOP 4.4)

用 Plane.io 做確認,子工作項狀態轉 Done 即代表需求方簽核通過,不另外要求書面簽名或其他系統。

### 4. 規格文件標準化模板

順延處理,待整體流程報告完成、定案後再進行(非取捨決策,純粹排序決定)。

## 影響

SOP 開放問題清單(第5節)由4項縮減為1項(僅剩規格文件模板)。流程主體視為定案,可以整理成報告。
