# 決策紀錄 0002:整合 Plane.io 工作單結構,調整估時機制

- 日期:2026-08-11
- 決策者:Cooper
- 狀態:已採用(骨架方向確認,細節待補)

## 背景

團隊已在使用 Plane.io 做專案管理。Cooper 說明實際運作方式:
1. PM 收到需求、確認後開立需求工作單,內容描述需求,並開立子工作項「規格文件」
2. PM 與企劃討論確定規格,再與開發組長開需求會議,各單位組長須充分了解需求內容與工作細項
3. 確認後開發組長回報開始與完成送測時間,開始開發
4. PM 與需求方回報時程、追蹤進度
5. 所有內容都開立對應工作單,由負責人填寫時間與工作內容

這與原本(決策0001)設計的抽象八階段骨架在精神上一致,但需要改用 Plane.io 的「父工作項+子工作項」結構描述,並且原設計的「PM初估 vs 開發實估」雙層估時比對機制,在實際流程中並不存在——PM 只在開工作單時寫一個粗估區間給需求方參考,不是正式比對標準。

## 考慮過的選項

### 選項 A:保留原八階段骨架,不特別對應 Plane.io 結構
- 優點:文件不用改動
- 缺點:與團隊實際操作工具脫節,無法作為可執行的操作依據,無助於解決「交接資訊遺失」痛點
- 結果:放棄

### 選項 B:將八階段改寫為 Plane.io 父工作項/子工作項結構,調整估時機制為單層(開發組長承諾制)
- 優點:與實際操作一致,子工作項本身就是交接載體,狀態變更即交接動作,可直接落地
- 缺點:原本「雙層估時比對」設計失去比對基準,需要重新設計時程追蹤機制(見 SOP 4.1,尚未定案)
- 結果:採用

## 決定

SOP 改為以 Plane.io 工作單結構呈現(需求工作單 + 規格文件/開發/測試/驗收/上線五個子工作項),角色新增「開發組長」「測試組長」作為需求會議與送測接手的窗口。測試組長不參與初期需求會議,送測後才接手。狀態欄採用 Plane 預設(Backlog/Todo/In Progress/In Review/Done)。

## 未決事項

原「PM初估 vs 開發實估」落差容錯機制因估時層級改變而失效,新的時程追蹤機制(開發組長承諾送測時間 vs 實際進度)三個選項列在 SOP 4.1節,待 Cooper 選定。
