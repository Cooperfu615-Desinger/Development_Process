# 決策紀錄 0005：平台規格書範例改放撰寫規範，原填寫範例移出分享版

- 日期：2026-09-02
- 決策者：Cooper
- 狀態：已完成（分享版部分）

## 背景

分享版「平台規格書範例」原本放的是一份填好的具體規格（會員前台 Lobby 個人資訊，17 章皆填真實數值）。Cooper 認為這份內容「很多地方會誤導」——具體功能的特定假設（VIP 分級數值、Mock 行為延遲、欄位命名）容易被誤讀成規格書格式本身的通用要求。Cooper 提供 `PLATFORM_SPEC_STANDARD.md`（一份定義章節結構、每章該寫什麼/不該寫什麼的撰寫規範），要求改放這份內容。

## 討論與決策

### 分類定位

討論是否要把這份內容移到分享版的「規則」分類（跟 Plane 開立規則同組）。Cooper 的看法：Plane 開立規則是「共用規則」，平台/遊戲 Plane 使用範例是「規則套用在各領域的範例」；但規格書沒有一份可以套用到兩個領域的共用規則（平台後台頁面 vs 遊戲數學設計，結構天差地遠），所以「XX規格書範例」這個位置本身就同時扮演「該領域的規範」角色，不是「範例」在套用另一份規則。

**結果：維持在「範例」分類位置與分組，不搬到「規則」。** 只把單項標籤從「平台規格書範例」改名為「平台規格書撰寫規範」，反映其規範性質。Cooper 同時表示日後也要用同樣邏輯調整「遊戲規格書範例」（目前仍是完整填寫的宙斯與黑帝斯250真實規格，尚未提供對應的遊戲規格撰寫規範來源，本次不處理，待後續另行討論）。

### 原填寫範例的去向

**結果：移出分享版，搬到 `docs/platform/examples/spec-example.md`（＋對應 `.html`）保留**，作為將來「具體規格長什麼樣」的參考範例來源；分享版不再內嵌其內容。因為 `docs/platform/examples/` 不是 git 版控目錄、不對外發布，這裡保留了原始 Plane 內部連結與完整真實數值，不像分享版需要做公開發布前的內容遮蔽。

### 適用範圍標示（後台 vs 整個平台）

`PLATFORM_SPEC_STANDARD.md` 原文的「適用範圍」寫明僅「後台功能頁、報表頁的規格書」，比「平台」整體窄（不含 APP/WEB 玩家前台，如剛移出的個人資訊範例本身就是玩家前台頁面，理論上不受這份規範約束）。Cooper 對是否要放大範圍表示無偏好，交由執行判斷。

**結果：忠於原文件，維持「後台功能頁、報表頁」的範圍標示，不放大。**
**理由**：放大範圍等於替 Cooper 做了一個未經驗證的涵蓋範圍宣稱；範圍不明時寧可保守陳述，之後若確認 APP/WEB 前台規格也要套用同一份結構，可另外調整或另立一份前台適用的規範。此為單一專案內、可逆的技術文字判斷，未觸及商業數值，故依 CLAUDE.md「純技術路線選擇...自行決定」原則直接執行。

## 追加：遊戲規格書範例比照調整（2026-09-02 同日追加）

Cooper 提供 `GAME_SPEC_HUMAN_TEMPLATE.md`（SlotForge 專案下的「人類撰寫版遊戲規格書模板」），並直接指示「遊戲規格書範例：宙斯與黑帝斯 250」可以移除。比照上面平台的處理邏輯執行：

- 分享版「遊戲規格書範例」整份換成「遊戲規格書撰寫規範」，內容為該模板的 15 章固定結構（0.版本歷史～14.交付與同步備註）與每章填寫規則／填寫提醒，不含任何具體遊戲的填寫數值。側邊欄與卡片標籤同步改名，位置不變。
- 原本完整填寫的宙斯與黑帝斯 250 內容，第一時間先比照平台那次「移出分享版、留檔備查」的做法，搬到 `docs/game/examples/spec-example.html` 保留——但這是執行判斷，不是 Cooper 的指示。Cooper 隨後明確指示「可以完整移除不用保留，直接刪除就好」，故 `docs/game/examples/spec-example.html` 已刪除，不留檔。與平台那次（明確指示搬去 spec-example.md 保留）的差異：平台是玩家前台頁面規格，遊戲是已被公司內部認定「會誤導」的填寫規則本身格式參考，兩者是否值得保留的判斷本來就不同，不是同一條規則的兩次不同執行。
