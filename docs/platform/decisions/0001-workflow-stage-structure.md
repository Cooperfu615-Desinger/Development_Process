# 決策紀錄 0001:開發流程階段骨架

- 日期:2026-08-11
- 決策者:Cooper
- 狀態:已採用(骨架方向確認,細節待補)

## 背景

團隊採 PM/企劃/開發/測試四個專職獨立角色,平台功能類專案(會員/金流/後台)。
主要痛點:
1. 各階段交接資訊遺失或不透明
2. 時程掌控不易,常 delay 或估錯

需要設計一套開發流程,從需求接收到交付,明確角色與交接產出物。

## 考慮過的選項

### 選項 A:精簡 4 階段(需求 → 規格 → 開發 → 交付)
- 優點:流程短,行政負擔小
- 缺點:PM初估與開發實估沒有獨立階段做落差檢查,測試也沒有獨立階段,不利於解決「時程估錯」與「交接遺失」兩個痛點
- 結果:放棄,粒度太粗,無法對應痛點

### 選項 B:8 階段(需求接收 / 需求確認與初估 / 規格文件 / 開發評估與排程 / 開發實作 / 測試驗證 / 驗收 / 交付上線)
- 優點:每個角色轉換都有獨立階段與書面產出物,PM初估與開發實估分開,可插入落差檢查點;測試獨立成階段,可放金流驗證要求
- 缺點:階段較多,行政成本較高
- 結果:採用。Cooper 確認「大方向對,可以往下細化」

## 決定

採用 8 階段骨架,詳見 `../SOP.md`。角色維持專職獨立,一人兼多角色時仍要求分別產出對應文件,不可省略書面交接。
