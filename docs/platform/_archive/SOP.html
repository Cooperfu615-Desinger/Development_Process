1. 角色定義

角色職責範圍
PM需求接收、開立工作單、跨階段協調、時程追蹤、對需求方回報進度
企劃需求轉規格、流程設計、UI/流程圖、驗收標準定義
開發組長參與需求會議、掌握需求全貌、回報開發起訖時間、分派工作給開發成員
開發依開發組長分派執行實作、單元測試
測試組長送測後接手,掌握測試範圍、分派測試工作
測試功能測試、迴歸測試、金流/金額專項驗證
需求方提出需求、最終驗收

一人兼多角色時(如企劃兼PM),仍須依角色分別在對應子工作項下填寫內容,不可省略只做口頭確認——避免同一人球員兼裁判時把「決定」跟「檢查」混成同一步。

2. 流程總覽(Plane.io 工作單結構)

需求工作單(父工作項,PM 開立)
 ├─ 子工作項:規格文件      (企劃)
 ├─ 子工作項:開發          (開發組長 → 開發)
 ├─ 子工作項:測試          (測試組長 → 測試,送測後才建立/啟動)
 ├─ 子工作項:驗收          (PM + 需求方)
 └─ 子工作項:上線          (開發 + PM)

流程順序:

PM收到需求並確認 → 開立需求工作單 + 規格文件子工作項
 → PM與企劃討論確定規格 → 需求會議(PM/企劃/開發組長)
 → 開發組長回報起訖時間、開立開發子工作項 → 開發實作
 → 送測,開立測試子工作項,測試組長接手 → 測試
 → 驗收子工作項 → 上線子工作項

PM 全程在需求工作單上追蹤各子工作項狀態,並對需求方回報進度。

各子工作項對應負責人與產出

子工作項負責人產出物(基本追蹤資訊反映於Plane,實質內容由各組自理,見4.4)交給下一階段的內容
(父)需求工作單PM需求描述、來源、粗估時程區間(非正式承諾)開立規格文件子工作項
規格文件企劃規格書(流程圖/欄位定義/驗收標準/決策紀錄)需求會議討論確認後的規格版本
開發開發組長→開發起訖時間(開始/預計送測日)、工時拆解、技術方案、程式+單元測試送測時的自測結果、已知限制
測試測試組長→測試測試報告(功能/迴歸/金流專項驗證)Bug清單、驗證紀錄
驗收PM+需求方驗收紀錄、差異項目簽核狀態
上線開發+PM上線紀錄、交付文件包最終交付物清單

Plane.io 狀態對應(使用預設狀態:Backlog / Todo / In Progress / In Review / Done)

工作項BacklogTodoIn ProgressIn ReviewDone
需求工作單(父)需求剛登記,未確認PM已確認,已開子工作項任一子工作項執行中驗收中交付完成
規格文件-待企劃撰寫企劃撰寫中/PM討論中需求會議討論確認中規格拍板
開發-待開發組長排入(規格拍板後開立)開發實作中內部自測、準備送測已送測
測試-待測試組長接手(送測時開立)測試進行中Bug修復/迴歸中測試通過
驗收-待需求方驗收驗收進行中-需求方簽核通過
上線-待排上線上線作業中-上線完成,交付文件包已送出

每個子工作項的狀態變更,即代表一次交接;負責人、起訖時間、目前狀態必須反映在 Plane 上,不可只用口頭同步取代——這是解決「交接資訊遺失」痛點的具體做法。至於規格書、測試報告等實質內容要用什麼工具管理,由各組組長自理(見4.4),不強制存放於 Plane。

3. 各階段詳細規範

需求工作單(父工作項)

  • 開立者:PM
  • 內容:需求來源、提出者、需求描述、粗估時程區間(給需求方方向感用,非正式承諾、不作為與開發組長實估的比對標準)
  • 離開條件:規格文件子工作項已開立
  • 常見風險:需求來源不明確 → 工作單內容必須留來源與提出者,不可省略

子工作項:規格文件

  • 負責人:企劃(PM協同確認)
  • 產出:規格書,內容包含:
    • 功能流程圖、欄位定義/資料結構、UI 稿(如適用)
    • 驗收標準(可測試、可勾選的條件,不是模糊描述)
    • 決策紀錄:為什麼這樣設計、放棄了哪些方案(對應 docs/platform/decisions/)
  • 交接動作:規格確定後,PM 召開需求會議(PM/企劃/開發組長參與),開發組長必須在會議中充分了解需求內容與工作細項,會議結論更新回規格文件子工作項
  • 離開條件:需求會議後規格拍板,開發組長回報起訖時間
  • 常見風險:規格寫完就丟給開發,決策脈絡沒留下 → 規格書內建決策紀錄段落,不是事後補;開發組長沒真的理解需求就點頭 → 會議紀錄需具體記下開發組長確認的工作細項,不是只記「已確認」

子工作項:開發

  • 負責人:開發組長 → 分派給開發
  • 產出:
    • 開發組長於需求會議後回報:開始時間、預計完成送測時間(填入 Plane 開發子工作項)
    • 工時拆解(依功能模組拆分)、技術方案摘要
    • 程式碼、單元測試
  • 離開條件:自測通過,送測(狀態轉 Done,同時開立測試子工作項)
  • 常見風險:
    • 規格理解落差 → 實作中若發現規格模糊,回頭找企劃確認並更新規格文件子工作項(不是自己猜)
    • 送測時間跳票沒人追蹤 → 見第4.1節時程追蹤機制

子工作項:測試

  • 負責人:測試組長(送測時才接手並開立此子工作項)→ 分派給測試
  • 輸入:程式碼、規格書驗收標準
  • 產出:測試報告,包含:
    • 功能測試結果(對照規格書驗收標準逐條勾選)、迴歸測試結果
    • 金流/金額相關功能的專項驗證:凡涉及金額計算、扣款、派彩、餘額異動的功能,測試報告必須附驗證方式(自動化測試案例、模擬情境、或實跑紀錄),純人工檢查不算驗證(對應 CLAUDE.md 不可妥協項目2)
  • 離開條件:Bug清單清空,或已知並經PM確認可上線的範圍
  • 常見風險:金額相關bug人工看過就算測完 → 明確要求可重現的驗證方式並存檔

子工作項:驗收

  • 負責人:PM + 需求方
  • 產出:驗收紀錄,含差異項目與簽核狀態
  • 離開條件:需求方簽核通過,或差異項目已列入下版規劃並取得共識
  • 常見風險:口頭說「可以了」沒留紀錄 → 驗收紀錄必須填在 Plane 工作項裡並歸檔

子工作項:上線

  • 負責人:開發 + PM
  • 產出:上線紀錄(時間、範圍、負責人)、交付文件包(給需求方的最終文件,含規格書、測試報告、驗收紀錄)
  • 離開條件:上線確認且需求方收到交付文件包
  • 常見風險:上線後沒人整理交付文件 → 交付文件包是本階段的硬性產出,不是選配

4. 跨階段機制

4.1 時程追蹤與落差處理機制已決定

新流程下,正式時程承諾來自開發組長在需求會議後回報的「開始時間/預計送測時間」,PM 在需求工作單上的粗估區間僅供對需求方溝通方向,不作正式比對基準。

機制:不設固定的自動化門檻(不用百分比或天數觸發規則)。PM 持續在 Plane 上追蹤各子工作項進度;一旦預期會delay,由 PM 直接與需求方協調——調整時程、範圍或優先順序,且這個協調可以在開發過程中隨時發生,不限定在某個固定檢查點。開發組長若判斷會delay,應主動反映給 PM,由 PM 決定是否要對需求方溝通。

不設死規則的原因:落差的處理仰賴 PM 對需求方關係與情境的判斷,不適合用固定百分比/天數取代;Plane.io 在本流程中只負責讓 PM 看得到進度(見4.4),協調動作本身在 Plane 之外進行。

4.2 決策紀錄

每個階段做出的重大決策與放棄的方案,寫入 docs/platform/decisions/,格式:一個決策一個檔案,含背景、選項、決定、理由。目前已有:

4.3 金流/金額相關功能的驗證要求

凡功能涉及金額計算、派彩、扣款、餘額異動,不論在哪個子工作項,只要產出「結論」(規格可行、測試通過、可以上線等),都必須附驗證方式(模擬、自動化測試、或實跑紀錄),純人工推導或人工檢查不算驗證。此規則對應 CLAUDE.md 全域規則,寫入本SOP以確保平台功能類專案(尤其金流模組)明確適用。

4.4 Plane.io 的定位與邊界已決定

Plane.io 沒有可標記「金流相關」「粗估區間」等資訊的自訂欄位功能,且 Cooper 確認 Plane.io 的定位就是:

  • 確認「有哪些工作項」(需求工作單 + 各階段子工作項)
  • 追蹤「目前進度到哪裡」(工作項狀態:Backlog/Todo/In Progress/In Review/Done)

除此之外的內容管理(規格書、測試報告、決策紀錄等實質產出怎麼寫、存在哪裡),由各組組長自行處理,SOP 不強制規定工具或存放位置。SOP 對 Plane 的唯一硬性要求是:每個工作項的負責人、起訖時間、狀態要反映在上面,確保 PM 能看到全貌並據此做4.1節的協調判斷。

驗收簽核:透過 Plane.io 做確認(子工作項狀態轉為 Done 即代表需求方簽核通過),不另外要求書面簽名或其他系統。
